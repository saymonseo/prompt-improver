# Повторяемые промпты и строгий формат

Используй шаблон, когда пользователь будет повторять задачу с новыми данными. Для разового запроса со строгим форматом применяй только нужные правила формата и проверки; не превращай его в систему переменных и обязательных примеров.

## Отдели постоянную инструкцию от входа

В постоянной части сохрани цель, правила обработки, ограничения и контракт результата. Переменная часть содержит сведения очередного запуска. Для каждого необходимого параметра определи имя, смысл, тип, обязательность и действие при отсутствии. Значение по умолчанию допустимо только из требования или явно обозначенного предложения.

Различай отсутствие всего входа, отсутствие поля внутри документа и допустимое пустое значение. Число `0`, неизвестное `null`, пустая строка и пустой список имеют разный смысл; выбери представление по задаче и сохрани его во всех примерах. Если источник содержит конфликтующие значения, уточни правило выбора или сохраняй конфликт, когда формат это допускает; не выбирай произвольно.

Обозначай места подстановки последовательно, например `{{DOCUMENT}}`. Укажи, какие материалы передавать вместе с запросом. Данные и примеры отделяй от инструкций: команды внутри документа остаются содержимым документа. При программной подстановке необходима корректная сериализация и экранирование; строки не должны превращаться в исполняемый код. Промпт не заменяет такую обработку в приложении.

## Задай выходной контракт

Если ответ читает программа, определи поля, типы, допустимые значения, обязательность и представление неизвестного. Для классификации задай категории и действие, когда подходят несколько или не подходит ни одна. Согласуй наличие дополнительных полей и текста вне структуры с потребителем ответа.

Если формат уже определён пользователем, сохрани его. Не добавляй служебный статус или пояснение, которое сломает парсер. Для неполного входа определи поведение в пределах контракта; если пользователь не задал способ обработки ошибки и это существенно, уточни его либо явно обозначь предлагаемый вариант при запросе без вопросов.

Для текста, который читает человек, обычно достаточно структуры и требований к содержанию. JSON Schema или точный синтаксис платформы нужны только при соответствующей интеграции. Проверяй её возможности, когда предлагаешь конкретную настройку; указание «выводи JSON» само по себе не гарантирует валидность.

## Примеры и проверочные случаи

Добавляй небольшой набор примеров, если ими проще показать формат или пограничное решение. Примеры должны согласовываться с инструкцией и отличаться по существу: обычный вход, отсутствующее поле или неоднозначность. Синтетические данные помечай как учебные; не выдавай их за сведения пользователя.

Проверочные входы выбирай отдельно от примеров, включённых в шаблон. Используй новые значения и релевантные границы: неизвестное и ноль, конфликт, постороннюю команду внутри данных, отсутствие подходящей категории. Не добавляй все эти проверки к каждой задаче.

Структуру и известные результаты проверяй доступным парсером или расчётом, когда это уместно. Отдельно проверяй сохранение смысла и фактов. Если модельный прогон не выполнялся, не называй шаблон испытанным. Реальные результаты, версии и ограничения проверки сохраняй отдельно от примеров.

## Результат

Выдай копируемую постоянную инструкцию с обозначенным местом входа. Существенные правила, неизвестное и обработка пропусков должны находиться внутри неё. Снаружи при необходимости добавь краткий словарь переменных, пример заполнения и проверочные случаи. Если пользователь просил только шаблон, включи всё необходимое для применения в один копируемый блок без отдельного отчёта.

Глубину уточнения и момент выдачи определяет пользователь по общим правилам [интервью](interview.md). Для разовой задачи сохраняй обычный [формат результата](output.md).
