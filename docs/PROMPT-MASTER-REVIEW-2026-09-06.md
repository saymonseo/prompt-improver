# Подробный разбор Prompt Master: что улучшить в Prompt Improver

Дата проверки: 6 сентября 2026 года. Это анализ опубликованных инструкций и выборочная проверка технических рекомендаций по первичным источникам. Новые модельные прогоны Prompt Master в рамках этого обзора не проводились.

**Рекомендация: сохранить нашу систему предметного брифинга и проверки фактов, а из Prompt Master перенять отдельные способы адаптации задания к среде, описания изменений и диагностики ошибок.** Самый полезный следующий шаг — усилить сохранение требований при сборке промпта. Затем можно добавить профили изображений и автоматизаций. Перенос всего чужого скилла принесёт и полезные приёмы, и противоречащие нашим требованиям ограничения.

## 2. Как устроен Prompt Master

Его основной маршрут: определить инструмент → извлечь намерение → выбрать шаблон → исправить типовые недостатки → добавить нужный контекст → проверить и выдать копируемый промпт. Уточнение ограничено тремя вопросами. В начале скилла закреплены основные правила, в середине — большая таблица маршрутов, в конце — контроль результата. [Основной алгоритм](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L7).

Из намерения извлекаются девять составляющих: действие, инструмент, формат, ограничения, входные данные, контекст, аудитория, критерии успеха и примеры. Это полезная схема проверки полноты. Однако название инструмента объявлено обязательным всегда, а ограничения — только для сложных задач. Для нашего продукта важнее выяснить условия, меняющие результат: даже короткое письмо может иметь обязательный запрет на упоминание имени или конкретный срок. [Таблица намерения](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L46).

Сильная сторона — широкий охват способов исполнения: текст, код, агент с доступом к файлам, поиск, изображения, видео, голос, автоматизации, 3D. При этом предметная область и среда исполнения — разные измерения. Сайт для автосервиса требует и понимания бизнеса, и сведений о разработке; выбор Cursor сам по себе не уточняет цель бизнеса.

| Задача | Prompt Master по тексту инструкций | Prompt Improver 1.2.0 |
|---|---|---|
| Быстро оформить понятное задание под инструмент | Центральный сценарий | Есть краткая выдача с учётом доступных возможностей |
| Последовательно выяснять неизвестную предметную задачу | Не более трёх уточнений | Пользователь выбирает продолжение, следующую тему и остановку |
| Разобрать плохой результат | Decompiler и диагностические паттерны | Отдельный режим debugging с наблюдением, гипотезой и проверкой |
| Подготовить повторяемый запрос | Шаблоны и примеры | Переменные, пропуски, строгий формат и отдельные проверочные входы |
| Передать контекст в новый чат | Явный Memory Block | Самодостаточный промпт, факты, неизвестное и поздние исправления |
| Адаптировать изображения и автоматизации | Специализированные маршруты | Общие профили; детализация этих форматов пока ограничена |
| Проверить фактическое основание | Запрет выдумок и маркировка уверенности; отдельные правила проверки документации | Происхождение сведений, применимость, доступность источника и пределы извлечения |

Последний столбец опирается на наши [интервью](../skill/prompt-improver/references/interview.md), [передачу результата](../skill/prompt-improver/references/output.md), [работу с основаниями](../skill/prompt-improver/references/evidence.md), [debugging](../skill/prompt-improver/references/debugging.md) и [шаблоны](../skill/prompt-improver/references/templates.md). Таблица описывает инструкции, а не измеренное превосходство одной системы над другой.

## 3. Разбор всех 13 шаблонов

Буквы соответствуют [файлу шаблонов Prompt Master](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/references/templates.md). Названия схем удобны для разработчика; пользователю необязательно выбирать между аббревиатурами.

| Шаблон | Практическая ценность | Решение для нашего скилла |
|---|---|---|
| A — RTF | Короткая задача и форма ответа | Сохранить краткий режим; роль не делать обязательным полем |
| B — CO-STAR | Разделяет цель текста, аудиторию, стиль и тон | Использовать как внутреннюю памятку редакторских задач, без обязательной анкеты |
| C — RISEN | Помогает описать итог, границы и зависимые шаги | Уже покрыто типами задач; фиксировать шаги только при реальной необходимости |
| D — CRISPE | Учитывает творческое направление и варианты | Полезны критерии различия вариантов; несколько описаний роли и личности избыточны |
| E — Auditable Reasoning | Просит проверяемые основания и результаты проверок | Уже есть; сохранять без требования скрытого хода рассуждений |
| F — Few-Shot | Показывает нужный формат на примерах | Уже есть более условный вариант; не переносить правило о неизменной пользе 2–5 примеров |
| G — File-Scope | Фиксирует текущее и желаемое поведение, совместимость | Расширить примеры нашего software-профиля; неизвестные пути сначала найти |
| H — ReAct + Stop Conditions | Описывает действия, границы и остановку агента | Взять структуру поручения; убрать безусловные запреты на dev server и остановку после двух ошибок |
| I — Visual Descriptor | Предмет, композиция, свет, стиль, ограничения | Добавить профиль визуального результата; параметры сверять с моделью |
| J — Reference Image Editing | Выделяет изменение и свойства, которые нужно сохранить | Один из наиболее полезных кандидатов; исправить смешение API и интерфейса, не обещать идеальное сохранение |
| K — ComfyUI | Уточняет checkpoint и режим работы | Полезен принцип проверки workflow; универсальные CFG и negative prompt не переносить |
| L — Prompt Decompiler | Разделяет анализ, адаптацию, упрощение и разбиение | Debugging уже есть; можно яснее описать режим «объясни структуру», не навязывая переписывание |
| M — Current Claude Task Brief | Цель, состояние проекта, границы, приёмка, доказательства прогресса | Полезная общая форма для длительной агентной задачи; не привязывать её смысл к одному бренду |

Шаблон H — текстовое описание поручения. Само название ReAct не создаёт цикл вызовов инструментов, независимое исполнение или контроль повторов. Эти свойства должны обеспечиваться средой. Аналогично, перечисление нескольких «экспертов» внутри одного промпта не создаёт независимую проверку несколькими моделями.

## 4. Приёмы, которые стоит взять на вооружение

### 4.1. Паспорт возможностей исполнителя вместо обязательного вопроса о бренде

В маршрутизации полезно различать чат, API, IDE и автономного агента. Но вопрос «какая нейросеть?» имеет смысл только тогда, когда ответ меняет постановку. Человек может ещё не выбрать инструмент. В этом случае нужен переносимый промпт и обозначенные требования к возможностям, а не остановка брифинга.

Предлагаемая внутренняя памятка:

| Сведение | Когда оно меняет задание |
|---|---|
| Тип результата | Текст, код, изображение, видео, голос, автоматизация |
| Среда исполнения | Чат с человеком, API с парсером, IDE с проектом, агент с действиями |
| Доступный вход | Текст, файлы, изображения, ссылки; что действительно можно прочитать |
| Инструменты | Поиск, вычисления, терминал, редактирование, внешние подключения |
| Модель и версия | Когда нужны конкретный синтаксис, лимит или параметр |
| Выходной контракт | Документ, структура данных, файлы проекта, изображение, последовательность действий |

Большая часть принципа уже есть в [output.md](../skill/prompt-improver/references/output.md). Новое улучшение — компактная маршрутизация и примеры для разных модальностей. Не нужно задавать пользователю все шесть вопросов, если ответы видны из контекста.

### 4.2. Раздельное описание изменений и сохранения исходника

В Template J полезна мысль: при редактировании требуется описать разницу с исходником. Для фотографии, текста и кода важны исходный материал, конкретная правка, свойства для сохранения и критерий проверки. [Template J](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/references/templates.md#L279).

Наш профиль редактирования уже содержит «что менять и сохранять». Его стоит дополнить визуальными случаями: какое изображение является исходным; какая область меняется; допустимы ли связанные изменения света и теней; должны ли сохраниться лицо, надписи, пропорции или положение предмета; есть ли техническая возможность редактирования.

Не нужно обещать пиксельную идентичность средствами, которые её не гарантируют. Также нельзя утверждать, что исходник осмотрен, если доступно только описание пользователя.

### 4.3. Блок актуального состояния с происхождением решений

Memory Block делает перенос контекста заметным и удобным. Но формулировка «все прошлые решения» недостаточна: среди них могут быть предложения модели, отменённые решения и ошибочные предположения. [Memory Block](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L437).

Для нас полезна следующая адаптация, включаемая только при существенной истории:

```text
Актуальное состояние задачи
- Подтверждено пользователем: …
- Обязательно сохранить в результате: …
- Позднее изменено или отменено: …
- Уже пробовали: действие, наблюдаемый результат, условия.
- Причина неудачи: подтверждена / предположена / неизвестна.
- Неизвестно или не предоставлено: …
```

Это предлагаемый формат, а не новый обязательный блок для каждого короткого запроса. Отменённые варианты стоит включать только когда их повторение вероятно. Такой блок не обеспечивает память между сессиями сам по себе: он должен попасть в контекст следующего исполнителя.

Связь с нашим аудитом конкретна: в случае 28 потерялось ограничение ответа в 500 слов. Перенос состояния должен сохранять числовые лимиты и запреты независимо от краткости итогового текста. В случаях 13 и 48 важно отличать отсутствие предоставленного результата от утверждения, что действие никогда не выполнялось. [Подтверждённые замечания аудита](../evals/AUDIT-50-2026-09-06.md).

### 4.4. Диагностика по наблюдаемому симптому

Каталог «симптом → изменение запроса» помогает чинить промпт точечно. Например: ответ нарушает JSON → проверить контракт; повторяет отвергнутый вариант → восстановить актуальные ограничения; ссылается на несуществующий файл → уточнить доступ и исходное состояние. [Диагностические паттерны](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/references/patterns.md).

В нашей версии 1.2.0 этот механизм уже есть в debugging.md. Полезное дополнение — несколько примеров ошибок для изображений, автоматизаций и переноса между средами. Не следует дублировать весь список из 37 правил в ядре или объявлять гипотезу о причине доказанным диагнозом.

### 4.5. Проверка актуальности параметров отдельно от постоянной логики

Model Recency Gate требует сверяться с официальными источниками при вопросах о новых моделях и конкретных параметрах. Это правильный принцип. Но в том же ядре остаётся большой список версий и настроек; часть старого профиля может примениться без запуска проверки. [Маршрутизация и проверка актуальности](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L68).

Для нас лучше хранить устойчивое правило: перед конкретной рекомендацией определить среду и версию, затем проверить нужную возможность. Если появится справочник параметров, у записи должны быть источник, область применимости и дата проверки. Истечение условных 60 дней не должно быть единственным триггером: доступность могла измениться раньше. Без доступа к документации — нейтральная формулировка и обозначенный пробел.

Интересная деталь: [открытый PR №48](https://github.com/nidhinjs/prompt-master/pull/48) предлагает вынести изменчивые сведения в отдельный датированный файл. Это предложение участника проекта; такого файла в проверенном main нет. Конкретные модельные утверждения самого PR в этом обзоре не сертифицировались.

### 4.6. Поручение агенту: исходное состояние → результат → полномочия → проверка

Template M удачно соединяет результат, контекст, область работы, допустимые действия и подтверждение выполнения. Эту структуру можно использовать для разработки, обработки файлов и автоматизаций. [Template M](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/references/templates.md#L395).

У нас уже есть границы изменений, реальные проверки и полномочия в [software.md](../skill/prompt-improver/references/domains/software.md). Полезно добавить короткий пример передачи проекта другому агенту. Подтверждение результата должно сообщать, что сделано и чем проверено; галочка после каждого микрошага не заменяет доказательство и может перегружать разговор.

### 4.7. Предметный профиль автоматизаций

Связка «событие → действие → передаваемые поля» значительно точнее пожелания «автоматизируй продажи». Это новое направление для отдельного небольшого профиля. [Workflow AI](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L358).

При адаптации добавить то, чего недостаточно в краткой схеме: что делать при пропущенном поле, повторном событии, ошибке внешнего сервиса; какой результат пользователь считает успешным. Наличие подключения должно быть подтверждено или указано как требование настройки. Фразу «сервис уже авторизован» нельзя выдавать за факт без основания. Секреты не помещаются в переносимый промпт.

### 4.8. Проверка полезности каждого добавленного условия

Аудит лишних фраз полезен: у каждой инструкции должна быть функция. Однако экономия длины не должна удалять реальные требования. Для нашего скилла правильный порядок: сохранить цель и обязательные условия → проверить основания → удалить дублирование → проверить копируемость.

Добавить контроль происхождения конкретики: число, файл, срок, технология, роль, причина, характеристика объекта — откуда это взялось? Допустимые основания: пользователь, прочитанный материал, проверенный источник или явно обозначенное предложение. Если основания нет, конкретика не становится обязательным условием.

## 5. Что переносить нельзя и что требует проверки

### Подтверждённые технические несоответствия

**DALL·E 3 и редактирование.** Template J рекомендует для DALL·E 3 Edit endpoint и одновременно требует интерфейс ChatGPT. Это смешивает разные поверхности исполнения. На дату проверки официальная карточка сообщает, что DALL·E 3 удалён из API; применять этот путь как рабочую текущую инструкцию нельзя. [Чужой шаблон, строка 288](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/references/templates.md#L288), [официальная карточка DALL·E 3](https://developers.openai.com/api/docs/models/dall-e-3).

**Обязательный negative prompt в ComfyUI.** Template K требует два блока всегда, хотя в официальном примере Flux.1 прямо указано, что negative prompt не нужен. Это проверяемый контрпример универсальному правилу. CFG 7 и другие значения из общего шаблона также нельзя автоматически переносить на любой checkpoint: в этом обзоре каждый sampler и параметр не тестировался. [Template K](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/references/templates.md#L312), [официальный пример ComfyUI Flux.1](https://docs.comfy.org/tutorials/flux/flux-1-text-to-image).

**Синтаксис исключений Midjourney.** README показывает `negative: …`, а основной скилл использует `--no`. Официальный параметр исключений — `--no`; текстовая метка `negative:` не является его эквивалентом. Мы не запускали генерацию, поэтому не утверждаем, что пример обязательно даст плохую картинку. Дефект — несогласованность заявленной настройки. [Пример README](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/README.md#L108), [документация Midjourney](https://docs.midjourney.com/hc/en-us/articles/32173351982093-No).

### Неподтверждённые универсальные правила

| Правило Prompt Master | Почему его нельзя считать универсальным | Что использовать у нас |
|---|---|---|
| Первые 30% промпта обеспечивают сохранность контекста; структура PAC2026 30/55/15 | В README нет ссылки на исследование этой пропорции; целевой поиск не установил первоисточник | Располагать цель и существенные ограничения заметно, проверять сохранение в длинных диалогах |
| Системный промпт reasoning-модели должен быть короче 200 слов | В прочитанной официальной рекомендации такого порога нет | Краткость по задаче без удаления нужных данных |
| Примеры всегда лучше инструкций для чувствительных к формату задач; 2–5 — оптимум | Польза зависит от задачи и модели; OpenAI рекомендует сначала попробовать без примеров | Добавлять примеры при необходимости, проверять на других входах |
| Каждая инструкция должна использовать самые сильные MUST/NEVER | Жёсткость не устраняет противоречия и может превратить пожелание в запрет | Различать обязательное условие, предпочтение и предложение |
| Правильный результат с первой попытки — единственная метрика | Без исполнения это нельзя проверить; первая попытка не измеряет безопасность, достоверность и устойчивость | Оценивать результат, сохранение требований, основания, число исправлений и стоимость |

Источники правил: [reasoning-профиль](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L123), [Template F](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/references/templates.md#L153), [финальная проверка](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L474), [упоминание PAC2026](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/README.md#L405).

Исследование *Lost in the Middle* показывает зависимость результатов от позиции информации на исследованных моделях и задачах; из него не следует универсальная пропорция 30/55/15. [Статья авторов](https://arxiv.org/abs/2307.03172). Официальное руководство OpenAI рекомендует простые, прямые инструкции и условное применение примеров; оно не устанавливает рассмотренный порог в 200 слов. [Reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices).

### Противоречия нашему продукту и внутренние несогласованности

- **Максимум три вопроса.** Несовместимо с требованием пользователя продолжать тематический брифинг до его решения остановиться. Быстрый режим можно предлагать, но не навязывать.
- **Обязательная экспертная роль.** В нашем сравнении 18 пар не обнаружено согласованного преимущества короткой профессиональной роли. Это не доказывает бесполезность ролей вообще, но оснований вставлять их всегда нет. Указываем необходимые обязанности, методы и границы компетенции; не приписываем модели диплом и практику. [Наш эксперимент](../evals/ROLE-AB-2026-09-06.md).
- **Автоматическое разбиение двух действий на два промпта.** «Объясни и исправь» может быть одной связной задачей. В самом Prompt Master это конфликтует с правилом одного копируемого блока. Разделять нужно по зависимостям, инструментам и проверке, сохраняя общий итог.
- **Обязательные пути, стек и числовые параметры при отсутствии данных.** Пример исправления может показывать хорошую конкретику, но не даёт права придумывать пользовательский проект. Неизвестный путь нужно найти; технологию предложить; объём согласовать или обозначить как предлагаемый.
- **Все прошлые решения как закреплённые.** Позднее исправление пользователя имеет значение. Старую архитектуру нельзя сохранять автоматически, если её уже отменили.
- **Уверенность как основание факта.** Маркер `[uncertain]` полезен, но уверенная модель тоже ошибается. Нужны источники и результаты проверок, а не только самооценка уверенности.
- **Запреты и подтверждения на любой шаг агента.** Безусловная остановка перед любой зависимостью или удалением файла может блокировать уже порученную работу. Границы определяются конкретной задачей и действующими полномочиями.
- **Документация расходится с ядром.** README обещает Universal Fingerprint из четырёх вопросов; ядро ограничивает все уточнения тремя и для неизвестного инструмента предлагает ближайшую категорию. Пример README показывает название framework и оценку токенов, хотя ядро скрывает название, а changelog говорит об удалении оценки. README объявляет сложные техники исключёнными, ядро допускает их при определённых условиях.

Последние несогласованности можно проверить в [README](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/README.md#L197), [правилах ядра](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L18) и [диагностике](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/SKILL.md#L396). Это статически наблюдаемые расхождения; их частота в реальных ответах здесь не измерялась.

## 7. Чему учат обсуждения самого проекта

**Размер ядра.** В [PR №13](https://github.com/nidhinjs/prompt-master/pull/13) предложено вынести профили инструментов и сократить основную инструкцию. В проверенной версии это не реализовано: SKILL.md содержит 496 строк и 4 867 слов по разделению пробелами. Это подсчёт слов, не токенов. Нам не стоит расширять ядро всеми брендами: нужные инструкции должны подключаться по типу задачи.

**Поведение при провале проверки.** [Issue №32](https://github.com/nidhinjs/prompt-master/issues/32) поднимает полезный вопрос: что делать, если контроль качества не пройден? Для нас ответ должен быть явным: восстановить пропущенное условие; при противоречии запросить приоритет, если брифинг продолжается; при остановке сохранить нерешённое внутри промпта; не объявлять постановку полностью определённой. Предложенную в issue безусловную замену чувствительных данных пересказом копировать не нужно: для некоторых задач точный обезличенный фрагмент необходим.

**Безопасность входного текста.** [PR №36](https://github.com/nidhinjs/prompt-master/pull/36) описывает сужение активации, обращение с вставленным промптом как с данными и удаление секретов. Эти принципы есть и в текущем Prompt Master, и у нас. Описание PR нельзя считать доказательством наличия каждого предложенного пункта в main: оценивать нужно актуальный файл.

**Установка и ожидания пользователя.** Сообщения [№19](https://github.com/nidhinjs/prompt-master/issues/19), [№23](https://github.com/nidhinjs/prompt-master/issues/23) и [№66](https://github.com/nidhinjs/prompt-master/issues/66) указывают на вопросы упаковки, разбора frontmatter и применения в разных средах. Это сообщения о конкретном опыте, а не доказательство текущей несовместимости всех установок. Для нас полезны отдельные проверяемые инструкции установки и чёткое объяснение, что пользователь получает промпт для следующего исполнителя.

**Отбор доказательств.** Issue №61 с заголовком о памяти и цене токенов оказался рекламным предложением стороннего сервиса. Его проценты экономии не использованы как результат тестирования Prompt Master. Количество issues и уверенность автора сообщения сами по себе ничего не валидируют.

## 8. Как рекомендации выглядят на практике

Следующие фрагменты написаны для объяснения предлагаемых изменений. Это не сохранённые ответы Prompt Master и не результаты нового A/B-теста.

### Магазин детской одежды из нашего брифинга

```text
Подтверждено: детская одежда до 10 лет, 1000 товаров,
10 категорий, русский язык. Нужны дизайн, прототип и работающий
магазин с оформлением заказов. Товарами управляет менеджер по продажам.

Позднее уточнение логистики: самовывоз в Краснодаре,
собственная доставка по Краснодарскому краю.
Доставку по всей России не считать подтверждённой.

Пользователь указал, что оплаты не будет. Не добавлять платёжную
интеграцию; если для дальнейшей работы нужно выяснить взаиморасчёты,
оставить это отдельным неизвестным, а не назначать способ оплаты.

Материалов нет. Адрес, цены, ассортимент, фото и отзывы не выдумывать.
Lamoda — указанное предпочтение к дизайну; конкретные цвета,
размеры и устройство страниц не считать согласованными требованиями.
Стек, домен, хостинг и наличие разработчика пока не установлены.
```

Следующая тема брифинга: «Технологии, размещение и сопровождение». Система объясняет, что это поможет выбрать способ запуска и поддержки магазина, и предлагает продолжить или собрать промпт сейчас. При продолжении начинает с наличия хостинга и человека для сопровождения; при остановке переносит неизвестное в итог. Это сохраняет пользовательский контроль и не требует выбрать конкретную нейросеть заранее.

### Изменение фотографии товара

```text
Исходник: приложенная фотография товара.
Изменение: заменить фон на однотонный светлый.
Сохранить: фактический цвет, форму, рисунок и надписи на одежде.
Не добавлять комплектацию или детали, которых нет на исходнике.
Проверка: сравнить исходник и результат по перечисленным свойствам.
Если исходник недоступен или инструмент не поддерживает редактирование,
сообщить, что требуется для выполнения; не заявлять, что фото изменено.
```

Цвет фона здесь задан в учебном примере. В реальном запросе он должен происходить из пожелания пользователя или быть обозначен как предложение. Конкретные параметры редактора добавляются только после определения среды.

### Исправление промпта для резюме

```text
Наблюдаемый дефект: в ответ добавлено достижение, которого нет
в предоставленных сведениях.
Исправление: все факты об опыте брать только из входных материалов.
Предложения по усилению резюме отделять от подтверждённых достижений.
Неизвестные числа не заполнять; сохранять места для уточнения.
Проверка: сопоставить каждое утверждение об опыте с исходными данными.
```

Такое изменение лечит показанную ошибку. Добавление роли «карьерный эксперт» само по себе не обеспечивает отсутствие выдуманных достижений.

## 9. Приоритеты реализации

| Приоритет | Изменение | Где реализовать | Проверяемый результат |
|---|---|---|---|

| P1 | Паспорт возможностей и проверка конкретных параметров | output.md или небольшой подключаемый справочник | Перенос между чатом, API и IDE сохраняет цель и не придумывает инструменты |
| P1 | Профиль изображений с различием создания и редактирования | Новый условно подключаемый материал | Есть исходник, изменение, сохранение и проверка; настройки соответствуют модели |
| P1 | Блок актуального состояния и пример передачи агенту | output.md и software.md | Поздние исправления переживают сжатие; разрешённая работа не блокируется шаблонным запретом |
| P2 | Профиль автоматизаций | Новый условно подключаемый материал | Понятны вход, поля, результат, повторное событие и поведение при ошибке |
| P2 | Короткие примеры диагностики разных модальностей | debugging.md или примеры | Исправление связано с наблюдаемым дефектом и сохраняет рабочую часть запроса |

Пункты P0 подтверждены нашим аудитом. P1 и P2 — обоснованные кандидаты развития, но их фактический эффект ещё предстоит измерить. Поведение скилла и версия 1.2.0 этим документом не изменяются.

## 10. Как проверить пользу изменений

Не следует сразу добавлять все рекомендации и затем оценивать общий результат. Сначала проверить отдельные механизмы, чтобы понимать причину улучшения или регрессии.

1. **Сохранение смысла при одинаковых данных.** Передать текущему и изменённому скиллу один и тот же полный бриф. Выполнять полученные промпты в свежем контексте, без скрытого дублирования пользовательских ограничений в обёртке исполнителя. Именно такое дублирование маскировало потерю лимита в случае 28.
2. **Качество самого брифинга.** Отдельно начинать с короткой идеи. Ответы испытательного пользователя брать из заранее зафиксированного набора фактов, включая «не знаю», изменение решения и остановку. Ветка диалога может отличаться; оценивать найденные существенные сведения и лишнюю нагрузку на пользователя.
3. **Новые пограничные случаи.** Проверить неизвестную модель, отсутствие браузера или вложения, отменённую технологию, уже данное разрешение, конфликт примера с правилом, выдуманный файл, неподдерживаемый параметр, редактирование изображения и повторное событие автоматизации.
4. **Контроль результата.** Для данных использовать парсер и проверку известных значений; для кода — релевантное выполнение; для изображений — осмотр с сопоставлением исходника; для фактов — источники. Красивый промпт не засчитывается как рабочий результат без соответствующей проверки.
5. **Сравнение условий.** При отдельном сравнении с Prompt Master использовать его зафиксированную версию и доступные ей штатные файлы, одинаковые инструменты и лимиты исполнения. Контроль без улучшателя получает те же существенные факты; короткий исходный запрос можно измерять отдельным условием, чтобы не путать эффект дополнительных данных с эффектом оформления.
6. **Надёжность оценки.** Повторять спорные случаи, скрывать названия условий от оценщиков, менять порядок ответов, проверять часть результатов человеком. Для заявлений о переносимости нужны разные модели; для модульности — реальная загрузка нужных файлов, а не только единая спецификация.

Основные показатели: потерянные обязательные условия, добавленные неподтверждённые факты, выполненные критерии результата, ошибки инструментальных настроек, соблюдение остановки брифинга и число ненужных вопросов. Дополнительные: суммарные токены и время всего процесса, число исправлений, понятность результата человеку. Длина итогового промпта сама по себе не является качеством.

Средние 9.95/10 и 9.96/10 из нашего 50-тематического аудита нельзя считать доказательством превосходства над Prompt Master: там не было такого контрольного условия, а оценивание имеет ограничения и эффект потолка. [Методика и пределы аудита](../evals/AUDIT-50-2026-09-06.md).

## 11. Авторство, ограничения и решение

Prompt Master распространяется по MIT, автор в лицензии — **Nidhin Joseph Nelson, 2026**. При копировании или существенной адаптации текста нужно сохранить предусмотренное лицензией уведомление об авторстве и разрешении. Этот обзор содержит собственный анализ; исходный скилл целиком не включён в наш проект. При реализации прямых заимствований следует добавить соответствующее уведомление и ссылку на исходный коммит. [Лицензия источника](https://github.com/nidhinjs/prompt-master/blob/2bd92518e26bf659e21e3d9ab90573fcf3ddeccb/LICENSE).

Проверены все опубликованные файлы выбранного состояния, но не работоспособность каждого из перечисленных инструментов. Техническая сверка охватила конкретные спорные правила OpenAI, ComfyUI и Midjourney и утверждение о размещении контекста. Другие характеристики моделей, голосовых, видео- и 3D-сервисов не следует считать проверенными этим отчётом. Обнаруженное противоречие инструкции указывает на риск; частоту неправильных ответов можно установить только отдельными прогонами.

**Решение для развития:** сначала исправить сохранение ограничений и происхождение сведений; затем добавить небольшие профили исполнения и редактирования. Сохранить управляемый пользователем брифинг, предметное исследование и проверку фактов. Из Prompt Master брать механизм, который решает наблюдаемую задачу, а его жёсткие значения и общие обещания проверять отдельно.
